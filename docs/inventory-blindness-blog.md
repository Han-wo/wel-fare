# 이미 가지고 있던 걸 안 쓰고 있었다: 남의 설계를 읽고 내 코드를 다시 본 기록

이 글은 남의 아키텍처 문서(여신 상담 챗봇 설계안)를 읽고 우리 RAG 에이전트에 적용할 것을 찾은 기록이다. 결과물은 커밋 몇 개지만, 정작 배운 건 설계가 아니라 **내가 무엇을 가지고 있는지 모르고 있었다**는 사실이었다.

## 1. 판정 주체가 정반대였다

덱의 주장은 한 줄로 요약된다. **"판단은 그래프가, 설명은 벡터가, 대화는 LLM이."** 여신은 규제 도메인이라 적격 판정이 결정적·설명가능해야 하고, 그래서 `EligibilityRule` 그래프가 판정을 전담한다.

우리와 대조해 보니 핵심 축에서 반대였다.

| 축 | 덱 (여신) | WelfareAI |
|---|---|---|
| **판정 주체** | Neo4j Cypher (결정적) | **LLM** (`ELIGIBILITY_SYSTEM_PROMPT`) |
| 조건 표현 | `Condition{dim, op, value}` 노드 | 자연어 텍스트 |
| 그래프 역할 | 심장 — 판정 전담 | 후보 부스팅 (`matchScore` → `+0.15`) |
| 근거 | `GROUNDED_IN → Basis` 노드 | 사후 substring 검증 |

우리 `inferFromOntology`는 `lifeStage 2점 + region 1점 + targetGroup 2점` 같은 **태깅 그래프**다. "이 정책엔 청년·서울 태그가 붙어 있다"를 세는 것이지 `age between 19~34`를 평가하지 않는다.

한 군데는 닮아 있었다. 덱의 `UNKNOWN → ask 목록`은 우리 `getClarificationRequest`의 `missingFields` → HITL 설문과 구조가 같다. "모름은 탈락이 아니다"라는 원칙까지 동일했다. 각자 도달한 결론이라 오히려 신뢰가 갔다.

## 2. 덱도 허술한 데가 있었다

배울 게 있다고 해서 다 옳은 건 아니다. 공정하게 짚으면:

**"LLM은 판단에 관여하지 않음"이 성립하지 않는다.** 판정 1단계가 `대화 → {age, income, dsr}` 구조화인데 이걸 LLM이 한다. 연봉 5천이 세전인지 세후인지, 부부합산인지 — 추출이 곧 판단이다. 결정성은 "facts가 맞다는 전제 하에"로 한정되는데 덱은 이 단서를 한 번도 달지 않는다. 컴플라이언스 논리로 LLM을 밀어내고 입구에 다시 세운 구조다.

**`우대` 규칙이 알고리즘에서 증발한다.** 스키마는 `rule_type: 적격/우대/배제` 3종을 선언하는데, 판정 결과는 `ELIGIBLE/REJECTED/POSSIBLE/NO_PRODUCT` 4종이고 우대가 없다. 관계 목록에도 `Rule → LoanTerms` 엣지가 없어서 **조건부 우대금리(급여이체 -0.2%p)를 매달 자리가 없다.** 여신 상담의 핵심인데.

**시스템 총비용이 한 줄이다.** "LLM 추출 + 사람 검수 (필수)" — 상품당 규칙 몇 개인지, 검수 주체가 누구인지, 규정이 바뀌면 며칠 걸리는지가 없다. "챗봇 코드는 무수정"은 사실이지만 비용이 코드에서 사람으로 이동한 것이지 사라진 게 아니다.

## 3. 적용점을 찾다가 — 데이터는 이미 있었다

덱의 `Condition{dimension, operator, value}`를 보고 "우리도 저런 게 있으면 좋겠다"고 생각하며 코드를 뒤졌다. 그러다 `Policy` 엔티티에서 이걸 발견했다.

```ts
@OneToMany(() => PolicyRequirement, (req) => req.policy)
requirements?: PolicyRequirement[];
```

`PolicyRequirement`를 열어보니 덱의 `Condition`과 거의 같은 모양이었다.

```ts
reqType: string;              // ← dimension
operator?: string | null;     // ← operator
minValue?: number | null;     // ← value
maxValue?: number | null;
```

그래서 누가 쓰나 확인했다.

```
$ grep -rn "requirements" src/modules/rag
>>> 참조 0건
```

**시더 4개가 전부 쓰고, RAG는 한 번도 안 읽고 있었다.** 소비자는 목록 API와 알림 스케줄러뿐이었다.

DB를 찍어보니 더 구체적이었다.

```
reqType             count   has_min   has_max
AGE                  2785      2785      2785
SELECTION_CRITERIA   1129         0         0
TARGET_DETAIL         201         0         0
```

청년정책 **2,785건의 연령 조건이 min/max까지 전부 채워진 채로** 놀고 있었다. 복지로 계열은 상세 API가 자유 텍스트만 줘서 `reqType`만 붙고 값은 비어 있는데, 온통청년만 `sprtTrgtMinAge/MaxAge`를 준다.

확정적으로 답할 수 있는 축 하나를 LLM 추측에 맡기고 있었던 셈이다. 덱의 `MISMATCH → REJECTED(사유 명시)`를 이 축에서 그대로 구현했다.

```
트레이스: 연령 조건 결정적 판정 :: 만 36세 기준으로 청년정책 6건 평가, 4건 미해당

답변: 💡 핵심 요약: 햇살론유스는 만 19~34세 대상의 청년 보증부 대출입니다
     — 사용자의 연령(36세)으로는 해당 정책의 연령 요건에 맞지 않습니다.
```

3치 판정(`MATCH`/`MISMATCH`/`UNKNOWN`)으로 만들었다. 덱의 핵심 논리를 그대로 가져온 것인데, **"나이를 모름"은 탈락이 아니다.** 생년월일 미입력 사용자에게서 정책이 전부 사라지면 안 되니까.

## 4. 685건을 잘못 죽일 뻔했다

구현을 끝내고 데이터 분포를 찍어봤다.

```
정상 범위             2039
둘 다 0 (제한없음)      685   ← ?
min만 0 (상한만)        52
max만 0 (하한만)         9
```

`0~0`이 685건. 실물을 보니 `K-패스`, `제주 크리에이터 경제 생태계 확장사업` 같은 **연령 무관 정책**이었다. 온통청년 원천이 "제한 없음"을 `0`으로 보내고, 시더의 `buildAgeInfo`가 문자열 `"0"`을 truthy로 받아 `만 0세 ~ 만 0세`를 만들고 있었다.

내 판정 로직대로면 `age 36 > maxValue 0` → **685건 전부 미해당**이다. 연령 무관 정책이 통째로 사라진다.

데이터를 안 찍어봤으면 조용히 틀린 채로 나갔을 것이다. 테스트는 통과했을 테고 — 내가 쓴 테스트는 내가 상상한 범위만 검증하니까.

정규화를 데이터 경계와 판정 함수 양쪽에 넣고, 사유 문장이 `"만 15세 ~ 만 0세"` 같은 원문을 인용하지 않도록 막았다. 센티널 케이스는 테스트에 박아뒀다.

## 5. 오탐을 고치기 전에, 오탐이 있는지부터

다음은 그라운딩 검증이었다. `answer-grounding.ts`가 답변의 `📋 [정책명]`을 뽑아 근거 문서에 있는지 substring으로 대조하는데, 오탐이 잦을 것 같았다.

이번엔 **고치기 전에 실제로 일어나는지부터 봤다.** 직전 세션에서 그럴듯한 가설이 세 번 연속 틀렸던 게 있어서.

```
트레이스 52건 중 → 그라운딩 경고 2건, 둘 다 정정 LLM(최대 6초) 실행

ungrounded: ["장애인활동지원 추가지원사업(충청북도)", "도비 장애수당(경기도)",
             "최중증장애인 24시간 활동지원(대전광역시)", "행복장애수당(이천시)", ...]
```

이 이름들을 코퍼스에서 조회했더니 **5건 전부 실제로 존재했다.** LLM이 괄호로 지역을 덧붙였을 뿐이다. 지자체 복지는 동명 정책이 지역마다 있으니 오히려 유용한 구별 표기인데, 그걸 환각으로 판정해 멀쩡한 답변에 6초와 엉뚱한 "정정 안내"를 붙이고 있었다.

나머지 1건은 달랐다. `공공임대주택(예: 영구·국민임대) - 경기도 사례(양주시 옥정단지 등)` — 이건 LLM이 합성한 레이블이지 정책명이 아니다. **진짜 잡아야 할 것.**

그래서 괄호 주석을 떼고 한 번 더 보되, 괄호 밖까지 합성한 이름은 여전히 걸리도록 했다. 두 사례를 실제 trace에서 가져와 골든셋에 박았다 — 오탐 통과와 정탐 차단이 양쪽 다 회귀 테스트로 잠겼다.

## 6. 구조가 막은 것은 막혔다고 말하기

세 번째는 "역질의를 정책 요구사항 기준으로" 바꾸는 것이었다. 지금은 이렇게 정한다.

```ts
const needsAge = YOUTH.test(question);
const needsRegion = DEADLINE.test(question) || FACILITY.test(question);
```

**"청년이라는 단어가 보이면 나이를 묻는다."** 검색된 정책이 실제로 뭘 요구하는지와 무관하다. 덱은 반대로 판정에서 UNKNOWN이 난 축만 묻는다 — "역질의는 설문지가 아니다."

그런데 그래프를 보니 `request_missing_info`가 `pre_route`보다 **먼저** 실행된다. 묻는 시점에 아직 검색을 안 했으니 정책이 뭘 요구하는지 알 방법이 없다. 제대로 하려면 ask 노드를 retrieval 뒤로 옮겨야 하고, 그건 HITL 재개 경로까지 건드리는 재배치다.

그래서 **하지 않았다.** 대신 데이터가 이미 있는 지점에서 되는 만큼만 했다 — 생년월일이 없는데 연령 조건이 걸린 정책이 검색되면 그 사실을 요약에 실어, LLM이 근거에 기반해 나이를 묻게 했다.

```
신청대상: 만 19세 ~ 만 34세인 청년·대학생
(사용자님 생년월일 미입력으로 본인 연령 충족 여부를 확인할 수 없습니다)
```

한계는 분명하다. LLM이 답변 안에서 묻는 것이라 HITL 설문 UI가 안 뜬다. 구조화된 재질문까지 가려면 앞서 말한 재배치가 필요하다. 절반만 했다는 걸 절반만 했다고 적어두는 게 다음 사람에게 낫다.

## 정리

| 항목 | 이전 | 이후 |
|---|---|---|
| 연령 조건 활용 | RAG 참조 0건 | 2,785건 결정적 판정 |
| 그라운딩 오탐 | 5/6건 오탐 → 6초 정정 | 괄호 정규화, 정탐은 유지 |
| 역질의 근거 | 질문 키워드 | 검색된 정책의 조건 (부분) |

jest 184개 통과, 실제 대화 3종 검증.

## 결론

이번에 얻은 건 아키텍처가 아니라 **재고 파악**이었다.

`PolicyRequirement`는 스키마도 있고 데이터도 2,785건 채워져 있는데 아무도 안 읽고 있었다. 남의 설계를 읽고 "우리도 저런 게 필요하다"고 생각한 그 기능이, 이미 절반쯤 들어와 있었던 것이다. 누군가 시더를 쓰면서 성실하게 채워놨고, 소비하는 쪽을 연결하지 않았을 뿐이다.

`grep -rn "requirements" src/modules/rag`는 3초 걸린다. 그 3초를 안 써서 며칠어치 오해를 쌓을 뻔했다.

그리고 두 번 다 같은 습관이 살렸다. 연령 판정은 **분포를 찍어봐서** 685건 오판을 피했고, 그라운딩은 **실제 trace를 열어봐서** 고칠 가치가 있는지 확인했다. 코드를 읽어서 성립하는 설명은 여러 개 존재한다. 어느 게 참인지는 재봐야 안다.

남의 설계를 읽고 배우는 건 유용하다. 다만 적용하기 전에 할 일이 하나 더 있다 — **그게 이미 우리 코드에 들어와 있는지 먼저 확인하는 것.**
