# 에이전트 최적화를 추측으로 하면 생기는 일: 틀린 가설, TTFB 35초, 0.36%짜리 안전장치

이 글은 WelfareAI의 RAG 에이전트를 최적화한 기록이다. 다만 성과 목록이 아니라 **가설이 틀리는 과정**에 대한 기록에 가깝다.

시작은 내가 내놓은 그럴듯한 진단이었다. "문화 복지가 검색에 안 잡히는 건 랭킹 문제다. 하이브리드 검색이 최근 커밋이니 리랭커 가중치나 sparse 매칭을 의심해 봐라." 코드를 읽고 낸 결론이었고, 커밋 히스토리와도 아귀가 맞았다.

**틀렸다.** 그리고 그 뒤에 이어진 최적화에서도 첫 가설은 계속 틀렸다. 매번 틀린 자리를 찾아준 건 측정이었다.

## 1. 랭킹 가설이 틀렸다

증상은 "주택·청년 복지만 나온다"였다. 랭킹을 의심하기 전에 실제로 질의를 돌려봤다.

```
"문화비 소득공제 알려줘"          → 문화비 소득공제 ✅
"문화생활 지원해주는 복지 뭐 있어?" → 통합문화이용권, 예술활동준비금 지원 ✅
```

검색은 멀쩡했다. 복지로 API 461건을 전수 조회해보니 통합문화이용권·스포츠강좌이용권·예술활동준비금이 다 적재돼 있었고, 시더에는 카테고리 필터도 없었다.

체감의 실체는 채팅이 아니라 **홈 화면 추천 질문**이었다. 첫 화면에 뜨는 6개가 전부 주거·장애인이라 "주택만 있네"로 읽힌 것이다.

그럼 추천이 문제인가? 여기서 또 한 번 틀렸다. 카테고리 다양성 로직을 넣었는데 결과가 그대로였다. 프로필 임베딩의 후보 24건을 직접 찍어봤다.

```
0.570 서울형 주택바우처   0.555 국민임대-남구   0.551 공공임대주택 공급
0.549 자녀출산 무주택가구  0.545 국민임대-남구   0.545 행복주택-관악구  ...
```

**임계값 0.45를 넘은 24건이 전부 주거였다.** 다양성 상한이 걸러낼 다른 분야가 후보 풀에 애초에 없었다. 원인은 `buildProfileText`가 만드는 `"36세 서울 1인가구 직장인 중위소득 200% 이하 무주택 …"`에서 **"무주택"이 벡터를 주거 공간에 고정**시키는 것이었다.

그리고 이건 버그가 아니다. 무주택 1인가구에게 주거 추천이 나오는 건 정상 개인화다. 고칠 값어치가 있었던 건 따로 있었다 — `lh_housing`·`applyhome`(임대단지·공고 목록, 코퍼스 8만 건 중 7만 건)이 후보를 잠식해 `"국민임대 - 남구"`가 추천에 6번 중복으로 뜨던 것. 추천은 제도 카탈로그에서만 뽑도록 소스를 좁혔다.

**교훈 하나.** 증상에서 원인으로 가는 경로는 보통 한 칸이 아니다. 랭킹 → 추천 → 프로필 텍스트로 두 번 갈아탔고, 매 칸마다 측정이 방향을 바꿨다.

## 2. TTFB 35초 — payload를 의심했지만 아니었다

에이전트 로직 자체로 눈을 돌려 파이프라인 타임라인을 찍었다.

```
agent@5.6s → search_welfare@10.9s → agent@62.1s → answer@68.1s
TTFB 35초 / 총 68초
```

두 번째 agent 호출이 51초를 먹고 있었다. 첫 가설은 컨텍스트 크기였다. 도구가 8건의 문서를 통째로 LLM에 밀어 넣으니 prefill이 클 것이다 — 그럴듯했다.

재봤다. **8건 합쳐 2,463자.** 병목이 아니었다.

남은 용의자는 모델이었다. 같은 프롬프트로 격리 측정했다.

| 설정 | TTFB | 총 |
|---|---|---|
| gpt-5-mini 기본 | **9.45s** | 12.29s |
| `reasoningEffort: 'low'` | 2.10s | 4.79s |
| `reasoningEffort: 'minimal'` | 1.00s | 4.34s |
| gpt-4.1-mini (비-reasoning) | 0.82s | 1.62s |

답변 노드가 **reasoning 토큰을 태우고 있었다.** 검색된 사실을 정해진 형식에 옮겨 쓰는 일에 추론 예산을 쓰고 있었던 것이다.

흥미로운 건 이 코드베이스가 이미 같은 판단을 내린 적이 있다는 점이다.

```ts
// reranker.service.ts
// 채점은 reasoning이 필요 없는 작업이라 비-reasoning 소형 모델을 쓴다
// (question-condenser와 같은 이유 — nano는 reasoning 토큰 지연이 큼).
```

리랭커와 질문 재작성기는 이미 비-reasoning 모델로 내려와 있었다. **가장 비싼 답변 노드만 예외로 남아 있었다.** 원칙은 있었는데 가장 큰 호출에 적용되지 않은, 흔한 종류의 구멍이다.

### 도구 선택은 희생되지 않는가

`agentNode`는 두 가지 일을 한 모델로 한다. 도구 선택과 답변 합성. reasoning을 내리면 도구를 잘못 고를 수 있다. 그래서 7케이스 벤치마크를 먼저 돌렸다.

```
기본        정확 5/7 | 5.58s/건
'low'      정확 5/7 | 2.92s/건   ← 정확도 동일, 속도 2배
```

`'low'`는 정확도 손실 없이 호출당 절반이었다. 두 등급으로 나눠 공용 팩토리(`agent-llm.ts`)로 묶고, 4개 그래프가 각자 만들던 `new ChatOpenAI`를 통합했다.

- **agent** (도구 선택 + ReAct 답변) → `'low'`
- **answer** (예산 소진 답변, 정정 부록) → `'minimal'`

결과는 TTFB **35.06s → 16.33s**, 다른 질문은 **36.06s → 11.89s**.

## 3. 정교한데 꺼져 있던 안전장치

`assess_retrieval`은 잘 설계된 게이트다. "질문이 지목한 정책이 검색 결과에 없으면 저신뢰로 보고, 기계가 1회 재검색한 뒤 그래도 없으면 사용자에게 재질문한다." 점수 절대값 대신 **엔티티 부재**를 신호로 쓴다는 판단도 한국어 임베딩 특성을 정확히 반영한 것이다.

그런데 지목 여부를 이렇게 판별하고 있었다.

```ts
const NAMED_PROGRAMS = ['기초연금', '생계급여', /* ... */];  // 하드코딩 30개
extractNamedPrograms(question) {
  return NAMED_PROGRAMS.filter((p) => question.includes(p));
}
```

목록이 비면 게이트는 무조건 통과 처리된다. 코퍼스는 **8,268건**이고 목록은 **30개**다. 즉 정책의 **99.6%는 이 보호를 못 받았고**, 뒤에 달린 `retry_search` → HITL 복구 경로 전체가 0.36%에서만 동작하고 있었다.

이런 종류의 결함은 로그에 안 남는다. 게이트가 조용히 통과시키는 것과 실제로 문제가 없는 것은 겉으로 구별되지 않는다.

고친 방식은 단순하다. 부팅 시 코퍼스의 정책명을 메모리에 적재하고(10분 TTL 갱신) 목록과 합친다.

```
정책명 인덱스 7211건 적재
```

오탐이 걱정이라 3자 이하 이름("보상금")은 제외하고, 긴 이름이 잡히면 그 부분 문자열은 같은 정책으로 보고 중복 배제했다. `@Optional` 주입이라 단위 테스트는 provider 없이 기존대로 돈다.

하드코딩에 없는 정책으로 검증했다.

```
$ "구직급여 알려줘"
✓ 게이트 작동: 지목된 정책(구직급여)을 검색 결과에서 확인했습니다.
```

## 4. 지금은 안 터지는 버그를 고칠 것인가

ReAct 루프의 종료 조건을 읽다가 순서가 눈에 걸렸다.

```ts
function shouldContinue(state) {
  if (state.answer) return 'save_message';          // ← tool_calls 확인 전에 탈출
  if (lastMessage.tool_calls?.length) return 'tools';
```

`agentNode`는 tool_call 청크 **이전에** 온 텍스트를 `answer`에 담는다. 모델이 `"먼저 검색해볼게요"` 같은 preamble을 내면 → `answer` 세팅 → **도구를 한 번도 안 돌리고** 그 preamble이 최종 답변으로 저장된다.

터지는지 확인했다. 현재 모델(gpt-5-mini)로 3개 질문을 흘려보니 툴콜 앞 텍스트가 하나도 없었다. **지금은 안 터진다.**

그래도 고쳤다. 이건 모델 교체 한 번이면 파이프라인이 통째로 무너지는 종류의 잠재 결함이고, 수정 비용은 조건 두 줄 순서 바꾸기다. 발현 확률이 아니라 **발현 시 손상 × 수정 비용**으로 판단할 문제다.

## 5. 고치러 갔다가 더 큰 걸 주운 자리

턴당 히스토리 쿼리가 2회였다. 후속질문 재작성과 그래프 `loadContext`가 같은 쿼리를 따로 날리고 있었다. 사소한 낭비라 캐시를 넣으려다 순서를 확인했다.

`onStart`(사용자 메시지 저장)가 그래프 실행보다 **먼저** 돈다. 그래서 `loadContext`가 읽는 히스토리에는 방금 저장된 현재 질문이 이미 들어 있고, 거기에 `HumanMessage(question)`을 또 붙인다. **매 턴 프롬프트에 같은 질문이 두 번 들어가고 있었다.**

캐시를 "저장 전" 시점으로 고정하니 중복 쿼리와 중복 질문이 같이 사라졌다. 원래 잡으려던 것보다 주운 게 컸다.

체크포인트도 비슷했다. `thread_id`가 턴마다 새로 생기는 `traceId`인데 정리 로직이 없어 턴당 11개씩 영구 누적되고 있었다. HITL 재개는 직전 턴 하나만 참조하므로 나머지는 전부 사문이다. 대기 없이 끝난 턴의 스레드를 즉시 폐기하도록 했다 — 턴당 증가 **11 → 0**.

## 정리

| 항목 | 이전 | 이후 |
|---|---|---|
| TTFB (2개 질문) | 35.06s / 36.06s | **16.33s / 11.89s** |
| 신뢰도 게이트 커버리지 | 30개 (0.36%) | **7,211개** |
| 턴당 체크포인트 증가 | ~11개 | **0개** |
| 턴당 히스토리 쿼리 | 2회 | 1회 |
| 프롬프트 내 질문 중복 | 2회 | 1회 |

jest 171개 통과, 문화 질의 회귀 없음.

## 남은 것

TTFB 16초는 여전히 높다. 현재 `agent 4.5s → retrieval 5.3s → 답변 첫 토큰 6.6s`이고, 답변 노드만 비-reasoning 모델로 완전히 분리하면 더 내려간다. `verify_answer`의 그라운딩 판정이 단순 substring이라 정책명에 괄호 하나만 붙어도 오탐이 나고, 그때마다 정정 LLM이 6초를 더 쓰는 문제도 남아 있다.

## 결론

이 세션에서 제일 많이 한 일은 코드 수정이 아니라 **가설 폐기**였다. 랭킹이라는 첫 진단이 틀렸고, payload라는 두 번째 가설도 틀렸고, 추천 다양성 로직은 넣고도 효과가 없었다.

세 번 다 코드를 읽고 세운, 나름 근거 있는 가설이었다. 그리고 세 번 다 측정 한 번에 뒤집혔다.

에이전트 시스템은 LLM 호출·검색·그래프 전이가 겹쳐 있어서 **읽어서 성립하는 설명이 여러 개 존재한다.** 그럴듯함은 변별력이 없다. 타임라인을 찍고, 후보 풀을 출력하고, 모델 설정을 바꿔가며 같은 프롬프트를 재보는 것 — 결국 이 지루한 작업만이 어느 설명이 참인지 알려준다.

가장 위험한 결함이 **가장 조용했다**는 것도 남는다. 게이트가 99.6%의 정책을 그냥 통과시키고 있었지만 에러 로그는 깨끗했고, 매 턴 프롬프트에 질문이 두 번 들어가도 답변은 멀쩡히 나왔다. 시끄러운 버그는 알아서 발견된다. 조용한 것들은 재보기 전까지 없는 것처럼 보인다.
